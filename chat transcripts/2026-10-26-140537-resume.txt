⏺ Your new idea makes sense, and I'd adopt it. Here's how I understand it, then
  my answer on voice.

  The idea:
  - Workbook (the side panel): holds the battery: each step's instruction,
    visuals and questions. Submitting answers and moving forward happens only
    here.
  - Chat: a conversation with the tutor about the workbook ("I don't get step
    2", "is it B?", "why was that wrong?"). Nothing said in the chat moves the
    student forward or records an answer.

  It's like a student with a worksheet and a tutor sitting next to them. Why it
  works:
  - Separate jobs: a question to the tutor can't accidentally count as an
    answer, and the student can talk freely without derailing their progress.
  - Cleaner measurement: answers come only from the workbook, and you can log
    how much the student talked to the tutor around each question.
  - A home for wrong answers: your choice after a wrong answer fits naturally.
    "Reveal answer" is a button in the workbook, and "Explain my thinking" opens
    a discussion in the chat.
  - A home for voice: voice belongs in the chat, while the workbook stays
    click-and-type, as you already decided.

  What needs deciding:
  1. Practice versus checks. If the tutor helps choose answers everywhere, the
     scores no longer show what the student knows alone. I'd split the
     activities:
     - Practice questions (the 3 steps): working them out with the tutor is
       fine.
     - Checks (the opening assessment and the final check): the tutor only gives
       hints and never confirms an answer before it's submitted.
  2. The tutor sees the workbook, but not the other way round. Each chat message
     includes what the workbook shows: the current step, and what the student
     has selected or typed but not yet submitted. Workbook events such as a
     submitted answer, a wrong answer or a finished step can prompt the tutor to
     speak. Nothing in the chat can change the workbook.
  3. Who introduces each step. I'd have the tutor introduce each step in a
     sentence or two in the chat, with the full explanation in the workbook.
     That keeps the chat a conversation rather than a lecture.
  4. Layout. The side panel becomes the main workspace, wider than an artifact
     panel and probably at least half the screen on desktop. On phones, the
     student switches between Chat and Workbook tabs.

  workbook still goes into the existing slot for a feature panel.

  Topics it proposes:
  - Statistics: positive results on screening tests. For example: a rare
    condition and a 90%-accurate test, so what's the real chance a positive
    means you have it? Most people answer around 90%; the right answer is about
    9%. The common mistakes are named and easy to spot. The visual is a grid of
    1,000 dots showing where the positive results come from.
  - Social science: the bystander effect. Why each person in a crowd is less
    likely to help. People usually blame personality ("people are selfish"), and
    the theory replaces that with causes in the situation. The visual is a
    five-step flowchart of how a person decides to help. The agent adds a
    caveat: newer CCTV studies show someone in a crowd usually does help, so
    Tutor shouldn't claim crowds make help less likely overall.

  Changes it implies for the plan:
  1. Fixed assessment and final-check questions. It has drafted these for both
     topics, with answer keys and scoring. If they were generated per session,
     they'd differ in difficulty and a before/after gain couldn't be trusted.
     The 3 teaching steps stay generated, since they're the feature under test.
     This reverses the plan, which generates the assessment.
  2. Two question sets, swapped: half of participants get set A before and set F
     after, and half get the reverse. This separates "this question was easier"
     from "they learned".
  3. A confidence control on check questions ("sure / think so / guessing").
     It's a small new UI element, used to compare how sure people felt with
     whether they were right.
  4. A participant ID in the URL (e.g. ?pid=P03) so a moderator can tie logs to
     a person.
  5. An optional follow-up 3–7 days later, run outside the app by a form or
     short call, to check retention. Schwartz, Bransford and Sears show early
     gains can fade.
  6. A concrete event log format, including flagging chat help given during
     check questions, so we can see if the tutor leaked answers.

  What the results can and can't show: with 5–12 participants and no comparison
  group, the results can show:
  - whether the questions tell people apart

  - where the flow breaks down

⏺ The statistics topic is base rates in a positive test result
  (stats.base_rates). The question is: if someone tests positive on a screening
  test, what's the chance they actually have the condition?

  The method the tutor teaches is to picture 1,000 people, count how many test
  positive with and without the condition, and compare the two groups. Most
  people get these questions wrong in two ways: they answer with the test's
  accuracy, or they ignore how rare the condition is.

  The first opening-check question (A1):

  ▎ 1 in 100 people have a condition. The test detects 90% of people who have 
  ▎ it. It also wrongly flags 9% of people who don't. Someone tests positive. 
  ▎ Roughly what's the chance they have it?

  The answer is about 9%. Out of 1,000 people, 9 true positives are swamped by
  89 false ones. The wrong answers are 90%, 50/50, and 1%.

  We never wrote the exact opening message for the test script. The measurement
  doc only says it must use different numbers from A1, so it doesn't give away
  the check. Any message like the topic's example questions, "If a test is 95% 
  accurate and I tested positive, what's the chance I have the disease?", will
  trigger the stats topic.

⏺ We haven't picked a host yet; neither plan mentions one. I'd steer away from
  Netlify for this app, for two reasons:

  - Time limits: Netlify runs servers as functions, and a normal function is cut
    off after 60 seconds, according to Netlify's docs. Generating Tutor step 1
    takes 75–86 seconds, and the full set of steps up to 160. Some Claude
    replies with thinking can also run past 60 seconds.
  - No disk: functions can't keep files, so the JSON files that store
    conversations, sessions and test events would be lost. Netlify's own storage
    (Blobs) would mean rewriting the repo layer.

  Netlify can work, but it means rewriting generation as background jobs plus
  polling, and moving storage to Blobs. That's a big change for a throwaway
  prototype.

  Better fit: a host that runs our Express server as an always-on process with a
  disk. It would serve the built app and the API together, with no code changes
  beyond a start script. Two options:
  - Render: connect the GitHub repo and add a small persistent disk for
    server/data. Roughly $7–8 a month. This is the quickest to set up. I 
    recommend this one.
  - DigitalOcean droplet: you already use DigitalOcean with GitHub Actions for
    Kirby. It's cheap, but you'd set up the server, HTTPS and the process
    manager yourself.

  Whichever host we pick, two things are needed:
  - A password on the site. A public URL lets anyone spend your Anthropic and
    ElevenLabs credits and see participants' data. A simple shared password for
    test administrators and participants is enough. This is a small server-side
    check, with no new dependency.
  - The API keys go in the host's environment settings, never in the repo.

  Which host should I plan for: Render, a DigitalOcean droplet, or Netlify with
  the rework?
