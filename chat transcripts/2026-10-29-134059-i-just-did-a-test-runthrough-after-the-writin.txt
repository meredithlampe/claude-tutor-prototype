⏺ Two GitHub Actions workflows would cover this without adding any dependencies.

  1. A check on every push. It runs typecheck, lint and build, then starts the
  server on a throwaway data folder. A small set of tests then hits the API
  using Node's built-in test runner:
  - the health check
  - the site password blocking and allowing requests
  - loading the page
  - the chat and Tutor endpoints that don't call Claude

  It needs no API keys and costs nothing. It catches code that breaks before
  Render deploys it.

  2. A scheduled check of the live site, every 6 hours. It checks that the site
  loads, that /api/health responds quickly, and that the password lets it
  through to a read-only endpoint. When a run fails, GitHub emails you. By
  default that goes to whoever last edited the workflow, which will be you once
  you push it.

  It sticks to read-only requests. The site's data is shared by everyone who
  uses it, so creating chats or Tutor sessions would clutter what the hiring
  team sees.

  The tradeoff: also check Claude and ElevenLabs?
  /api/health only shows that the server is up, not that the API keys still
  work. The scheduled check could also send one tiny Claude request and check
  the ElevenLabs key. That means adding both keys to GitHub's secret settings,
  and costs fractions of a cent per run. GitHub keeps secrets hidden even though
  the repo is public. I'd add it: an expired key or used-up credits is the most
  likely way this breaks without anyone noticing.

  A note on agents: the frontend-engineer agent covers client/ and server/, so

⏺ Most of the wait is Claude writing SVG diagrams. Each step is a single Claude
  call that writes everything at once:
  - the step's instruction and its visual
  - the step's question, often with its own visual
  - a parallel question with its own visual, which only appears if the learner
    gets the first question wrong

  So step 1 can mean three SVGs written one after another. Steps 2–3 can mean
  six, plus two final-check visuals for topics Claude writes from scratch. That
  matches the times in your recent sessions: about 65–72s for step 1, and about
  95s for steps 2–3.

  These are ranked by impact for the effort.

  1. Write the text first, then draw visuals in parallel. (biggest win)
  - How: one call writes only the text of steps and questions. Each visual is
    then its own small call, all running at the same time. The redraw path in
    checkedVisual (server/tutor/battery.ts:344) already draws one visual from
    text, so it can be reused.
  - Result: the wait becomes "text plus one visual" instead of "text plus every
    visual in a row". Step 1 could drop from about 70s to about 25–35s.
  - Option: show the text as soon as it's ready, with a placeholder where the
    visual will appear.

  2. Write parallel questions only when they're needed.
  They're only shown after a wrong answer, so most are never used. Write them in
  the background once the step is showing, or on demand at "Try a similar
  question". This roughly halves what each step call writes.

  3. Don't make step 1 wait for grading.
  - Now: step 1 waits for every opening-check answer to be graded first
    (session.ts:211). Grading the written answer is itself a Claude call.
  - Fix: start step 1 as soon as the last answer is submitted, and give Claude
    the raw answers to judge itself in the same call.
  - Saves: the grading time, probably 10–20s. Worth measuring.

  4. Use a faster model for the mechanical parts.
  Everything runs on Opus 5.5 with thinking on. Drawing visuals, writing missing
  scenario sentences and redraws could use Sonnet 5.5 or Haiku 5.5 with
  thinking off. Keep Opus for writing the steps themselves. The tradeoff is some
  risk to SVG quality, so check them visually before switching.

  5. Write steps 2 and 3 as separate calls running at the same time.
  Both start when step 1 appears. Step 2 is ready sooner because it no longer
  waits for step 3 to be written. The catch is that step 3 can't see step 2, so
  it needs a short outline of the steps decided up front to avoid repeating
  ideas.

  6. Pre-write content for the library topics.
  - How: write steps ahead of time for each likely misconception, then pick the
    right set at runtime. The topics are fixed and the opening check already
    comes from topic files.
  - Pros: almost no wait for the hiring team's demo.
  - Cons: less tailored to each learner, and more content to check by hand.

  7. Make the wait feel shorter.
  Use the gap for something useful, like the tutor asking a short reflection
  question in chat, rather than a spinner. This doesn't cut the time, but
  distraction is the actual problem, and it pairs with any of the above.

  My recommendation: 1 + 2 + 3. Together they cut what each call writes and when
  it starts, without changing the learning design, and I'd expect the step 1
  wait to drop below 30s.

  Claude's thinking time, and how much each call writes) to confirm where the
  time goes. That way we'd know the gains are real rather than estimated.

  to go ahead now, or save this for after the submission?
